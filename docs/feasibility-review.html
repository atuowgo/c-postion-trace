02能力级可行性分析

每个能力给出：实现路径、依赖 API、失败模式、降级链、以及 Phase 0 的验证手段。评级含义——成熟 API 与原理均有保证；需实测 原理成立但参数需真机数据；有约束 存在已确认的平台限制，需按修正方案实施。

1 楼层定位 —— "锁车后走出式"气压测量 可行 · 需实测
实现路径
不在驾驶进库时测（App 无法保证后台存活），而在锁车触发后开启气压计，记录用户从车位走到地面参考点的相对高度变化。层差 = 高度差 ÷ 3m。电梯、扶梯、楼梯均有效。找车时反向提示"车在你下方 N 层"，到层后气压归零校核。
物理余量
一层 ≈ 3m ≈ 0.36 hPa；iPhone 气压计短时相对精度约 ±0.05 hPa（≈±0.4m）。信噪比约 7:1，余量充足。几分钟时间窗内天气漂移（通常 <0.02 hPa/10min）可忽略。主要不确定性是电梯轿厢增压与空调风压，需分段取"高度平台期"而非瞬时值。
依赖 API
CMAltimeter.startRelativeAltitudeUpdates · CMPedometer.floorsAscended/Descended（7 天历史回查）· VNRecognizeTextRequest（楼层牌 OCR）
失败模式与降级链
气压实测（自动）→ 计步器楼层历史（补录，电梯无效）→ 拍楼层牌 OCR→ 通知一键选层（B1/B2/B3）
Phase 0 验证
2–3 个商场地库，电梯/扶梯/楼梯各走一遍，统计层差判定准确率；目标 ≥90%。
2 层内定位 —— 面包屑 + 车位快照 + 信标接力 可行 · 分场景
实现路径（按场景拆分，工程上必须分开评估）
场景 A · 原路返回：锁车后 PDR 面包屑（CMPedometer 步距 + CMDeviceMotion 航向）记录"车位→电梯"，找车时倒放为"直行 40 步 → 右转"式指令。限 300 步内，目标是带进目视/信标范围，不追求米级。
场景 B · 换出口返回：面包屑失效。无室内定位基础设施时纯软件无通用解——这是本方案唯一明确承认的软件边界。通用解为车内蓝牙信标：到层后沿主车道行走，进入信号范围（实测预期 20–60m）即接力能力三。零硬件保底 = 车位号/分区照片（电梯厅分区图与商场找车机均可对照）。
失败模式与降级链
面包屑倒放（原路）→ 信标接力（换出口）→ 车位号/分区快照（永远有效）
Phase 0 验证
PDR：150 步往返回放，终点误差 ≤15m 即达标。信标：地库实测发现距离（车身屏蔽衰减是主要变量）。
3 直线定位 —— 三层距离接力 可行 · 有平台约束
实现路径
室内无 GPS，必须依赖车内信标。按距离接力：Find My 网络（路人 iPhone 匿名上报，"车在这一带"）→ BLE RSSI 冷热（20–60m）→ UWB 箭头（10–30m，米级 + 方向；iPhone 17 U2 芯片范围约为 U1 的 3 倍）。
平台约束（已确认，方案已按此修正 → 见 03 节 F1）
AirTag 的蓝牙广播身份周期性轮换加密（防跟踪设计），第三方 App 无法通过 CoreBluetooth 稳定识别某个特定 AirTag；其 UWB 精确查找也仅开放给系统"查找"App。因此：App 内冷热指示改用 iBeacon 协议标签（固定 UUID，公开 API：CoreLocation 测距 + 后台区域监测）；AirTag 的价值保留在 Find My 网络粗定位与系统 UWB 箭头（App 深链跳转"查找"）。App 内一体化 UWB 箭头需 NearbyInteraction 认证配件，归入档位 2。
依赖 API
CLBeaconRegion / CLLocationManager.startRangingBeacons（iBeacon 测距，成熟十年）· NearbyInteraction（档位 2）· 查找 App 深链
Phase 0 验证
AirTag + iBeacon 各一枚放车内中控台：实测地库 BLE 发现距离、Find My 位置刷新时效、系统 UWB 接力距离。
T 支撑能力 —— 锁车自动触发（一切记录的前提） 可行 · 需实测
实现路径
主通道：快捷指令个人自动化"断开车机蓝牙 → 立即运行（无需确认）→ 调用 App Intent"。这是 iOS 上第三方获取锁车信号的唯一官方通道（App 直接监听蓝牙断开不被允许）。触发后 App 获得后台执行窗口，串行启动气压记录、面包屑、拍照提醒。兜底：CMMotionActivityManager 7 天历史回放"驾驶→步行"切换时刻，App 未存活也能事后补录；再兜底为手动一键记录。
依赖 API
App Intents（iOS 16+，后台执行）· 快捷指令自动化（蓝牙断开触发器）· CMMotionActivityManager.queryActivityStarting · beginBackgroundTask + 定位后台模式（延长记录窗口）
已知不确定性
① 自动化触发延迟与成功率（个别 iOS 版本对"立即运行"有过行为变化）；② App Intent 触发后的后台窗口时长（基线 ~30s，申请定位后台模式后预期分钟级）——这两项直接决定气压/面包屑能记多完整，是 G1/G2 关门项。
用户前置条件
iPhone 与车机完成普通蓝牙（音频/免提）配对；首启 30 秒引导建自动化。注意：车企 App 的 BLE 蓝牙钥匙不在系统设备列表，不能作触发器。

03关键工程发现（评审中确认的事实）

影响方案形态的三个结论，均已吸收进上文实现路径。

F1 · AirTag 不能被第三方 App 扫描 —— App 内冷热指示改用 iBeacon

AirTag 出于反跟踪设计轮换其蓝牙标识，CoreBluetooth 无法锁定特定 AirTag；UWB 精确查找仅限系统"查找"App。修正：档位 1 硬件从"一个 AirTag"改为 AirTag（Find My 粗定位 + 系统 UWB）+ iBeacon 标签（App 内冷热，约 ¥30），或档位 2 自制信标一体覆盖。

F2 · CoreMotion 历史可回查 7 天 —— 漏记从"灾难"降为"折损"

活动切换（驾驶→步行）、步数、上下楼层数均可事后查询。即使自动化未触发、App 未运行，打开 App 仍能补录停车时刻与近似楼层，只损失气压精测与面包屑。

F3 · "换出口返回 + 零硬件"是明确的软件能力边界

无室内定位基础设施时该场景纯软件无通用解。产品层面必须做预期管理：零硬件档位的承诺是"楼层 + 车位号照片"，不是"步步导航"。这不是实现缺陷，是物理约束。

04系统架构

纯客户端架构，无后端，数据不出设备。传感器/定位/蓝牙全部隔离在协议后，领域层可用录制数据回放测试——这是本项目可测性的关键设计。

09开发计划与 Phase 0 关门项

Phase 0 不写产品代码，只回答"参数是否达标"。四个关门项（Gate）各对应一个验证 Demo，任何一项不达标即触发对应降级链，不阻塞主线。

  1. 触发链路：蓝牙断开 → 自动化 → App Intent 后台执行
    达标线：触发成功率 ≥95%，延迟 ≤30s；同时测出后台窗口时长基线
  2. 走出式气压判层（2–3 个商场地库实测）
    达标线：电梯/扶梯/楼梯三种方式下层差判定准确率 ≥90%
  3. 信标实测：iBeacon 地库发现距离 + AirTag Find My 刷新时效 + 系统 UWB 接力距离
    达标线：iBeacon 车内放置发现距离 ≥20m
  4. PDR 面包屑往返误差
    达标线：150 步往返终点误差 ≤15m（目视可见范围）

10工程结论

  • 确定可行（API 与原理双保证）：历史补录、车位快照 OCR、iBeacon 冷热雷达、楼层一键选层、全部存储与 UI。这些构成任何情况下都成立的产品底座。
  • 大概率可行（原理余量充足，参数待 Phase 0 实测）：走出式气压判层（信噪比 7:1）、自动化触发链路、PDR 面包屑。
  • 已明确的边界（不是缺陷，是物理/平台约束）：换出口 + 零硬件无步步引导（F3）；AirTag 不可被 App 扫描（F1，已改 iBeacon）；App 内 UWB 箭头需专用配件（归档位 2）。
  • 工程属性健康：无后端、无私有 API、无商场依赖、权限按需请求、领域层可回放测试；最大的外部依赖是"用户建一条快捷指令自动化"，且有两级兜底。

建议：批准进入 Phase 0。四个验证 Demo 约 1–2 周，其中 G1 在自家车位即可完成，G2–G4 需一次商场地库实测。
