总览

三阶段共 10 个工作周（2026-07-13 启动 → 2026-09-20 三能力完整），外加按需的 Phase 3。资源假设：1 名 iOS 开发（全职）+ 产品负责人兼实测员（即你本人，累计约 4 个半天的实车/商场实测）。计划的骨架是三个里程碑：M0 关门决策（W2 末）→ M1 MVP 可日常使用（W6 末）→ M2 三能力完整（W10 末）。所有排期估算按此资源假设线性伸缩。

08测试策略

层级手段覆盖目标
单元测试（持续）领域层纯 Swift，用 Phase 0 起持续录制的传感器数据作回放 fixture（AltitudeSource 等协议的回放实现）楼层分段算法、状态机转换、面包屑压缩/倒放、置信度决策——不进地库就能回归的部分最大化
集成测试（每 Epic）真机脚本化场景：模拟定位 + 录制数据注入触发→记录→落盘→找车全链路
实地测试（4 次）固定 checklist 的实测①–④（见各 Phase）只验证无法在实验室复现的物理参数
Dogfooding（M1 起）TestFlight 日常使用 + App 内一键对错反馈真实分布下的成功率指标，喂给 Phase 2 调参

度量口径（App 内调试页常显）：自动触发成功率、判层准确率、快照完整度（有照片/有层差/有面包屑的比例）、找车用时。M1/M2 验收即读此看板。

09计划级风险与应对

技术风险已在可行性评审中覆盖，此处只列影响排期的风险。

风险触发点对排期的影响与应对
G1 不达标（触发成功率 <95%）M0E1 改为"半自动 + 补录为主"形态，工作量不变，产品承诺降级；不顺延
G2 不达标（判层 <90%）M0E2 重心移到一键选层 + 计步推断，气压转为辅助；E2 估算 -1d
实测排不出时间（依赖产品本人）各实测点关键路径上只有实测①②；③④可与开发并行，延迟只影响验收时点不阻塞开发
iOS 26.x 更新改变自动化行为随时补录链路独立于自动化，最坏退化为"打开 App 补录"；升级前留观察版本
单人开发的估算偏差持续Phase 2 已含 5d 缓冲；M1 范围内 E6（补录器）可降级为手动补录入口，省 1.5d

10协作方式与变更管理

  • 节奏：周一计划 / 周五对进度；里程碑各开一次决策会（M0 必须同步过实测数据再拍板）。
  • 产品负责人的全部投入清单：W1 前完成采购与蓝牙配对；实测①②③④共约 4 个半天；M1 起日常 dogfooding 顺手点对错反馈。其余时间无需参与。
  • 代码与文档：开发在 claude/car-location-tracking-wlrh7v 分支进行；DESIGN.md 是唯一事实来源，M0 的任何形态锁定、以及实施中偏离设计的决定，当天回写 DESIGN.md 并在 commit message 注明。
  • 范围纪律：Phase 1/2 期间的新想法一律进 Phase 3 Backlog，不插队；唯一例外是 M0 数据驱动的形态调整。
